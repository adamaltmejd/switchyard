# pinfold 0.0.7 on the e2e suite

Follows `2026-09-28-e2e-cli-hash.md`, same host and suite, pinfold 0.0.6 to
0.0.7. 0.0.7 fixes pinfold #63 (a build with unchanged inputs returns the
existing image id), #64 (a pinfold-built base is never pulled) and #65
(`pinfold image rm NAME`).

## Changes in Yard

- 0.0.7 refuses a box spec with a `user` field (pinfold #66). Yard sent
  the daemon's uid and gid, and pinfold never read them. The field is gone.
- The project image no longer carries a `dev.yard.project` label. Nothing
  read it.
- The harness retires the names of its images with `pinfold image rm`
  instead of `podman rmi --force` on their ids. An id can now carry more
  than one name, and `rmi --force` would take one out from under a
  running box. An image no box reported, such as one built for an
  execution capacity held back, is not retired; it has no mapped copy.
- A harness wait fails when the daemon raises `red:error`. The first 0.0.7
  run refused every `box up`, and each test sat out its 10-minute deadline;
  G3 failing that way now fails in 5 seconds. The six files that wait on a
  held model request still wait for its own deadline.

## Timing

| Call | 0.0.6 | 0.0.7 |
|---|---|---|
| `image build`, 62 calls | 326 s | 74 s |
| first `box up` from its image id | 546 s (62) | 242 s (52) |
| `box list`, 64 calls | 39 s | 591 s (median 9.8 s) |
| Pi runs, 109 calls | 263 s | 208 s |
| wall | 6.5 min | **6.1 min**; 5.2 min on a second run |

Builds are cheap, but each project still pays one uid-mapped copy on its
first `box up`: pinfold labels each build with its name, so identical
builds under two names are two ids (pinfold #67). `box list` is not slower
by itself; both versions wait about 2.5 s behind one copy in progress.
With builds fast, more first starts overlap, and the `box list` in each
test's `yard init` reconcile waits behind them. That wait took most of
what the fixes saved.

One id across names would leave one copy per run: about 3 minutes by the
same arithmetic as the previous note.
