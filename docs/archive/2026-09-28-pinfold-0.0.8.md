# pinfold 0.0.8 on the e2e suite

This follows `2026-09-28-pinfold-0.0.7.md`, on the same host and suite,
after the code cleanup. It moves pinfold from 0.0.7 to 0.0.8, which fixes
pinfold #67: identical builds under different names now share one image
id, and no image carries the `dev.pinfold.image` label.

## Changes in Yard

None in the binary. Nothing in Yard read the label.

The harness looked up each image name from the store's image ids through
that label. The lookup would now find nothing, and a shared id also carries
other tests' names. Every pinfold wrapper on a machine's daemon `PATH` now
records the NAME of each `image build`, and the teardown retires exactly
those names. That also retires a name no box reported, which the id lookup
missed.

## Timing

| Call | 0.0.7 | 0.0.8 |
|---|---|---|
| `image build`, 62 calls | 74 s | 23 s |
| distinct image ids a `box up` reported | 52 | 3 |
| first `box up` per id | 242 s | 12 s |
| `box list`, about 65 calls | 591 s (median 9.8 s) | 286 s (median 4.2 s, p90 7.5 s) |
| wall | 6.1 min, 5.2 min on a second run | **3.3 min** (198 s), 55 of 55 |

51 names built three distinct inputs. `box list` is now the largest
pinfold cost. This run doesn't show what it waits on. Under 0.0.7 it waited
behind `box up`s in progress.

## Image names

`image rm NAME` keeps NAME's tags while any box uses the id, including
another name's box (pinfold #68). Since ids are shared, a test's teardown
usually finds another test's box still running the fixture image. In this
run, 31 of 51 names kept their tags. They point at the three shared
images, so they cost no disk, but each run adds names. Running
`pinfold image rm` by hand after the suite retired them.
